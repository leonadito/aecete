# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Django rebuild of the AICITI institutional site. Read [PRD.md](PRD.md) before making content or
scope decisions — it defines every page, the reference content migrated from the live site
(aiciti.com.br), and the restricted "Acessos" area (builders/brokers login, section 12-A).

## Stack

Django 5 + Tailwind CSS v4 (standalone CLI, no Node/npm) + Alpine.js + HTMX (both vendored as
local static files, not CDN) + SQLite + WhiteNoise. Containerized with Docker for VPS deployment.

## Commands

```bash
venv\Scripts\activate                     # Windows; source venv/bin/activate on Linux/macOS
python manage.py runserver
python manage.py migrate
python manage.py makemigrations <app>
python manage.py test
python manage.py seed_all                 # idempotent: seeds board, benefits, FAQ, partners, blog
python manage.py createsuperuser

# Tailwind CSS build (run in a separate terminal during dev)
./tailwindcss.exe -i ./static/src/tailwind/input.css -o ./static/css/output.css --watch
```

Docker: `docker compose up --build` (needs a `.env` copied from `.env.example` first).

## Architecture

Five Django apps, each owning its own models/views/urls/templates/admin/seed command:

- **`pages`** — Home, Sobre, Benefícios, Dúvidas. Models: `BoardMember`, `Benefit`, `FAQItem`.
  Also hosts `context_processors.site_info` (nav items + contact info shared by header/footer/
  contact page across all apps) and `sitemaps.py` (aggregates the sitemap for every app).
  `nav_items` is a list of dicts, not tuples — a plain item has `label`/`url`, a dropdown item
  (currently only "Acessos") has `label`/`children`; `header.html`/`footer.html` branch on
  whether `item.children` is present. The "Acessos" children swap to "Minha área"/"Sair" when
  `request.user` is already an authenticated builder or broker.
- **`partners`** — model `Partner` with a `kind` field (`PARTNER` / `MEMBER_AGENCY`) covering
  both the "Parceiros" page and the "Imobiliárias associadas" home section from one model —
  don't split this into two models without checking the PRD's reasoning first.
- **`blog`** — model `Post`. `post_list` view returns the full page or just
  `blog/partials/_post_list.html` depending on `request.htmx` (django-htmx), so pagination
  works via HTMX without duplicating the template.
- **`contact`** — model `ContactMessage` + `ContactForm`. The submit view always saves the
  message to the DB before attempting to send the notification email (email failure must
  never lose a submitted message); email send is wrapped in try/except.
- **`portal`** — the restricted "Acessos" area (PRD section 12-A). Models `Builder` (a construtora
  account, `OneToOneField` to `auth.User`, intentionally independent from `partners.Partner` — see
  the PRD before linking the two) and `PriceTable` (a builder's price table: title, description,
  image, drive link). Brokers/agencies are just `User`s in the `Corretores` group (created by a
  data migration, `portal/migrations/0002_corretores_group.py`) — no separate profile model, since
  they only need read access. There is no self-signup: accounts are provisioned by AICITI staff
  directly in Django Admin (create the `User`, then the `Builder` pointing at it, or add the
  `User` to `Corretores`). `portal/views.py` has `is_builder`/`is_broker` helpers plus
  `BuilderRequiredMixin`/`BrokerRequiredMixin` — reuse those rather than re-deriving the role
  check from `request.user` elsewhere. The "Acesso ao Roll" menu entry is a static external link
  (`https://tramandai.aiciti.com.br/login?logout`) with no view behind it.

Shared templates (`templates/base.html`, `templates/partials/header.html` and `footer.html`)
live at the project root, not inside an app, and are included by every page. Static assets:
`static/src/tailwind/input.css` is the Tailwind source, `static/css/output.css` is the build
output (gitignored, regenerated by the CLI — never edit it by hand), `static/vendor/{alpine,
htmx}/` holds the vendored JS files (also not from a CDN, per PRD deploy constraints).

Content seeding uses per-app management commands (`seed_board`, `seed_benefits`, `seed_faq`,
`seed_partners`, `seed_blog`) orchestrated by `pages/management/commands/seed_all.py`, all
using `update_or_create` keyed by a natural key (name/question/title) — safe to re-run.

Real photos/logos migrated from the live site (board headshots, partner and member-agency
logos, benefit illustrations, the one real blog post's cover) live in `seed_media/<subdir>/`
(committed to git — this is source content, unlike `media/` which is gitignored runtime
uploads). Seed commands copy these into `MEDIA_ROOT` via `pages/seed_utils.py:attach_image()`,
which no-ops if the model instance already has an image — safe to re-run, and won't clobber
an image an admin user has since replaced by hand. When adding a new seeded image, drop the
file in the right `seed_media/` subdir and call `attach_image()` from the seed command; don't
commit anything under `media/` directly.

Site-wide chrome images (real AICITI logo, favicon, hero photo, inner-page banner) are
`static/img/*` — also pulled from the live site, but these are template assets, not
per-content-item uploads, so they don't go through `seed_media/`/`attach_image()`.

Brand colors (`brand` #262d90, `brand-dark`, `brand-light`, `accent` #ff141f — the AICITI
navy/red from the real logo) are defined in the `@theme` block of
`static/src/tailwind/input.css`. Use `bg-brand`/`text-brand`/`bg-accent` etc., not generic
Tailwind palette colors like `sky-*`, so new pages stay visually consistent with the rest of
the site.

## Constraints from the PRD worth remembering

- Authentication is in scope only for the `portal` app's restricted "Acessos" area — don't add
  login/signup anywhere else without checking the PRD first.
- No public self-signup for the restricted area: builder/broker accounts are created manually by
  AICITI staff via Django Admin, not through a form on the site.
- SQLite is the deliberate choice for this low-traffic institutional site — don't introduce
  Postgres without checking with the user first.
- No Node/npm anywhere in dev or in the Docker build — Tailwind is built via its standalone
  CLI binary only.
